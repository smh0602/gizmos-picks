## 2 · The 403 — NOT settleable from here either, and here is the proof

⛔ **This sandbox cannot make an unauthenticated `api.github.com` call.**
Its GitHub layer overrides `Authorization` unconditionally. Driven three
ways:

| request | result |
|---|---|
| default | `X-RateLimit-Limit: 15000` (its own app token) |
| `-H "Authorization;"` (explicit empty) | `X-RateLimit-Limit: 15000` |
| `-H "Authorization: Bearer ghp_0000…"` | `X-RateLimit-Limit: 15000` |

…and for a repository outside its allow-list it answers with its own
JSON refusal, not GitHub's. Same outcome as Cowork, different mechanism.
**The probe you specified has to run on the runner.**

### What I could measure, and it de-risks #91 more than the stub did

✅ **#91's real code, against the real server and the real cross-host
redirect.** `_raw()` pulled the live asset — `github.com` →
`release-assets.githubusercontent.com` → **530,498 bytes** of real 2026
data — with a sentinel token in the environment:

```
_auth_for("https://github.com/…")      -> ['User-Agent']
_auth_for("https://api.github.com/…")  -> ['Authorization','User-Agent','X-GitHub-Api-Version']
SENTINEL SEEN OFF-HOST: NONE
```

### 🔴 And one fact nobody has recorded: the DATA is reachable today

The release **download** path is not the API and is not rate-limited with
it. It worked unauthenticated, first try, just now. **The outage is
confined to name DISCOVERY**, not to the bytes.

⚠️ **And discovery genuinely needs the API** — measured, both ways:

```

pbp_participation/pbp_participation_2022.csv      206   <- only the uncompressed one exists
```

So `FILES`' template alone is not sufficient and `nfl.py`'s comment about
irregular names is correct. ➡️ **A fallback exists if the token does not
clear the 403** (fetch by template, fall back to the API only when the
template misses), but that is a design change and it is yours to call.

## 9 · Moving the ledger into the repo — the size is a non-issue, the
## visibility is the whole decision

### The size, measured three ways

Synthetic ledger seeded at **1.61 MB of markdown** (today's store), then
30 further slates at ~46 KB each, `git gc --aggressive` after each stage:

| design | pack after import | after 30 slates | per slate |
|---|---|---|---|
| **one append-only `.md`** | **278.31 KiB** | **531.32 KiB** | **8.4 KiB** |
| one dated `.md` per slate | 311.40 KiB | 590.87 KiB | 9.3 KiB |
| one cumulative `.md.gz` | 274.17 KiB | **1023.47 KiB** | **25.0 KiB** |

Against the repo as it stands — `repo_watch.py`, today: **109.64 MiB
pack, 5.44 MB/day packed growth**:

- the whole history imports for **278 KiB = 0.25% of the pack**, about
  **three hours** of current growth;
- ongoing cost **8.4 KiB/slate = 0.15% of a day's growth**.

🔴 **Rule 285, confirmed at 3.0x.** Gzipping the ledger looks *cheapest*
at import (274 KiB) and is **the most expensive inside a month**, because
git cannot delta a gzip and stores every rewrite in full. ⛔ Do not gzip
it.

⚠️ **And do not invert rule 285 for text.** One dated file per slate —
correct for gzips — costs **11% more** here than one growing file,
because each new file pays fresh zlib overhead with no delta base.
